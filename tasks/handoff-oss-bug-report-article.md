## 記事の骨格（草案に実装済み）

```
リード     同じ型の間違いを3回踏んだ、という宣言
第1部      3幕構成 ── 誤りの記録
  幕1        「キーが無い」→「機構が無い」と読んだ
  幕2        同じ型を2回（検出0件→検出力ゼロ／grep で空文字列を判別できず）
  幕3        差し戻し → 本当の切り分け → 再現手順 → 報告
  結び       失敗の記録は反証可能性の代わりになる
第2部      調査と報告の勘所（再利用可能な形）※切り出し可
終章       AI と一緒に調べたとき人間はどこで効いたか ※切り出し可
```

**構成の意図**: 時系列（プラグイン調査 → 課金先 → 有用性測定 → バグ発見）ではなく、
「同じ型の誤りを3回踏む」を骨格にしている。時系列にすると前半が個人的な環境事情で
埋まって読者に無関係になるうえ、動機の部分に公開できない要素があるため
（後述の「公開制約」）、構成側で回避している。

読者は幕1で「観測手段の範囲 ≠ 事実の範囲」という補助線を受け取り、
幕2では著者より先に誤りに気づける設計。幕3の差し戻しが伏線回収になる。

## 公開制約（重要）

元の調査は業務端末で行ったため、**そのまま書けない要素がある**。
草案は既に抽象化済みだが、加筆するときは以下を守ること。

**書いてはいけないもの**

- 社名・組織名・内部ホスト名・内部URL
- LLM ゲートウェイのエンドポイント、トークン、予算額、課金額
- 業務リポジトリのパス

**抽象化して書くもの**

- 調査の動機。元は「会社のゲートウェイに課金が飛んでいるのはコンプラ的にまずい」だったが、
  記事では**「自分の推論の癖」**に置き換えてある。ここを具体化しない
- プラグインの実行環境に関する記述

**書いてよいもの**

- プラグイン名・バージョン・issue 番号・OSS のコード引用（すべて公開情報）

## 残っていた判断の詳細（記録として保持）

### 1. 記事を何本に分けるか

| 案 | 内容 | 備考 |
|---|---|---|
| 1本 | 第1部＋第2部＋終章 | 現状の草案。約530行あり長い |
| 2本 | ①第1部＋第2部 ②終章 | 終章は AI 文脈なので読者層が違う |
| **3本** | ①第1部 ②第2部 ③終章 | 各部が独立見出しになっているので分割は容易 |

3本にする場合、②と③は①への内部リンクを張る前提。
草案では第2部・終章の見出しに `（独立記事に切り出し可）` と明記してある。

### 2. エージェント名・プラグイン名を出すか

草案の本文中はエージェントを「A」「B」と伏せ字にしてある。

- **issue URL を載せる**なら、リンク先に実名があるので伏せ字の意味が消える → 実名にする
- **載せない**なら伏せ字のままでよいが、具体性と検証可能性が落ちる

**判断基準**: この記事の価値は「誰でも再現できる観測」にある。
再現手順を載せるなら対象を特定できないと意味がないので、**実名 + issue URL を推奨**。

### 3. issue URL を載せるか

載せると具体性が上がるが、**upstream が修正すると記事の一部が過去形になる**。
「2026-08-06 時点」と明記しておけば陳腐化は許容できる範囲。

### 4. タイトル

草案の title は仮。候補:

- OSSのバグを見つけて報告するまでに、3回同じ間違いをした（現行）
- 「無い」と言うには、探し方の正しさを証明しないといけない
- コメントが宣言した契約を、コードが守っていなかった話

1つ目は物語寄り、2つ目は方法論寄り、3つ目は技術寄り。分割するなら
①に1つ目、②に2つ目を割り当てる形が素直。

## 記事の中身を確認したいとき（元セッションの事実関係）

草案に書いてある内容の裏付け。加筆・推敲で事実を確認したくなったときの参照用。

### 見つけたバグ

`security-guidance` プラグイン 2.0.6 の `hooks/sg-python.sh`。
Python インタプリタの選択で、探索リストが `python3.13` 止まりのハードコード。

```bash
for cmd in "python3.13" "python3.12" "python3.11" "python3.10"; do
```

**根本原因**: 同一ファイル内で抽象度が非対称だった。

| 機構 | 実装 | 新リリースを越えられるか |
|---|---|---|
| 互換性の判定（`is_sdk_compatible`） | パターン `3.1[0-9]｜3.[2-9][0-9]｜[4-9].*` | ○ |
| 対象の探索（Pass 1） | 列挙 | **×** |

つまり「3.14 が非対応と判定される」のではなく「**3.14 が発見されない**」。

**契約違反である根拠**: Pass 1 のコメントが自ら契約を宣言していた。

```
# Highest available wins; the user doesn't have to PATH-prefer it.
```

これが2通りに破れる（下記の再現手順）。

**再発性**: 1つ前の同種バグ（同リポジトリ #2071「LLM review silently disabled on
default macOS Python 3.9」）の修正がこの列挙を追加したもの。**修正が再発を内包していた**。

### 再現手順（記事に載せるもの）

**A: 「最も新しいものが勝つ」の破れ（マシン非依存）**

```bash
d=$(mktemp -d)
for v in 3.12 3.14; do
  printf '#!/bin/bash\nif [ "$1" = "-c" ]; then echo "%s"; else echo "SELECTED %s"; fi\n' "$v" "$v" > "$d/python$v"
  chmod +x "$d/python$v"
done
PATH="$d:$PATH" bash <plugin>/hooks/sg-python.sh /dev/null
```

観測: `SELECTED 3.12`（古い方が選ばれる）

**B: PATH 優先設定が実質必要になる**

`python3` が 3.9 を指し 3.10〜3.13 が不在の環境では、インストール済みの 3.14 が
発見されず 3.9 が採用される。結果:

```
ModuleNotFoundError: No module named 'claude_agent_sdk'   # 素の import
SyntaxError: invalid syntax (session.py, line 578)        # venv 注入後
```

「モジュールが無い」ではなく「構文が読めない」＝バージョン不一致の証拠。

### 3回踏んだ誤り（第1部の中身）

| 回 | 観測 | 誤った読み替え | 実際 |
|---|---|---|---|
| 1 | manifest に hook のキーが無い | 機構が存在しない | 別ファイル `hooks.json` で定義する形式だった。公式 README の3段落目に明記されていた |
| 2 | ログ上、150回実行して検出0件 | 検出能力が無い | ログにファイル名が無く対象の素性が不明。加えて実装が **API 失敗時も「脆弱性なし」と記録**していた |
| 3 | `grep '^VAR='` がマッチする | 値が設定されている | 空文字列にもマッチする。測りたかったのが「空文字列か否か」なのに判別できない道具だった |

### 差し戻しの内容（幕3の転回点）

作業相手から2つの指摘があり、報告の質が変わった。

> 本当にこれはバグなのだろうか。もう少し検証してみたい。

> そもそも Python ってもっとバージョンたくさんあるはずだし、
> 一部のバージョンしか指定していないのってなんか違和感がある。

前者で報告を止め、後者が「判定は原理・探索は列挙」という核心につながった。

### 終章の中身（人間が効いた4箇所）

| 指摘 | 型 |
|---|---|
| 「本当にこれはバグなのだろうか」 | 結論の停止 |
| 「一部のバージョンしか指定していないのは違和感がある」 | 前提への疑い |
| 「OSS なら誰か報告してるのでは」 | 探索空間の拡張 |
| 「下書きなくね？」 | 成果物の実在確認 |

4つとも**進める介入ではなく、止めて枠組みを問い直す介入**。
公平のため「効かなかった場所」（ログ集計・実装読解・対照実験の設計・英語の issue 執筆は
任せて問題なかった）も草案に書いてある。ここを削ると自賛か自虐に振れる。
